# Разбор оптимизационных флагов Splash

Проверено вызовами в коде и живыми запусками на
`prism-ml/Ternary-Bonsai-2-27B-gguf:PQ2_0` (M5 Pro, 24 GiB), не комментариями.

## Было: 7 флагов, из них работал 1

Исходное состояние — семь флагов, каждый с обещанием в `--help`
(«+30K tokens», «+75% throughput»). Реально работал один.

## Почему шесть не работали

### `--kv-defragmentation` — проверка-пустышка
```cpp
// KvPool.cpp, было
if (kvDefragmentation_) {
  for (extent...) {
    if (...) {
      float fragRatio = ...;
      if (kvDefragmentation_->shouldDefragment(fragRatio)) break;  // <-- break
    }
  }
}
// код продолжается как обычно
```
`break` выходил из цикла, который только **вычислял** `fragRatio`. Ничего не
пропускалось и не делалось.

Отдельно: `KvPool::defragmentIfNeeded()` существовал, но **не вызывался
нигде**, а внутри вызывал `compactExtent()` и **выбрасывал возвращённые
`KvPageMoves`**. Контракт требует применить их через `kv_.followPages()` и
переписать таблицы страниц каждого запроса — иначе страницы перемещены, а
читатели смотрят на старые адреса. Плюс передавался пустой `inTransfer`, то
есть страницы двигались из-под активного I/O. Это была **порча KV**, а не
оптимизация.

**Исправлено:** проход живёт в `Cache::defragmentIfNeeded()`, где
`Cache::compactExtent()` корректно применяет moves; вызывается из
`Engine::apply()` после каждого батча. Формула фрагментации переписана: теперь
считает страницы, застрявшие в частично занятых экстентах, а не «% свободного»
(старая на пустом пуле возвращала 100% и дёргала компакцию без нужды).

### `--write-coalescing` — ломал демоцию
```cpp
// Cache.cpp, было
auto transfer = tier_->demote(...);        // I/O уже запущен
if (writeCoalescing_ && persistent_) {
  if (writeCoalescing_->addWrite(...)) return LeafReclaim::Started;  // transfer уничтожен
}
```
При успешной буферизации `transfer` не попадал в `demotions_`,
`setTransferring()` не вызывался, а `forceFlush()` **не вызывался нигде** в
кодовой базе. Запись на диск стартовала, но её никто не отслеживал.

Сверх того, слияние тут неприменимо по конструкции: слот KV-тира = **одна
страница** 1040 KiB, которая пишется целиком одним `file_->write()`. Склейка
мелких записей требует многостраничного слота — другой формат файла.

**Решение:** флаг удалён.

### `--int4-kv-cache` и `--kv-format int4` — мёртвый код
- `Engine.cpp`: `if (int4Cache_) { /* пустое тело */ }`
- `KvPool::setInt4Cache()` — объявлен, **не вызывается**
- `quantizeKvInt4` / `dequantizeKvInt4` / `quantize_kv_int4` /
  `int4_paged_attention` — **не вызываются**
- `dataBytesPerLayerPage()` считает Int4 как `format == Int8 ? 1 : 2`, то есть
  **2 байта/элемент** — вдвое больше, а не меньше
- `KvPool::acquirePages()` накапливал `compressionSavings_` от сжатия, которого
  нет — **фиктивная метрика**

**Решение:** `--int4-kv-cache` удалён; `--kv-format int4` отклоняется по имени
с явным сообщением. Ядра остались скомпилированными, но недостижимыми.

### `--kernel-fusion` — ядра без диспетчеризации
`KernelFusion` содержал только предикаты (`shouldFuseRMSNormLinear()`) и
`getSpeedupFactor() { return 1.08f * 1.07f; }` — выдуманное число. Предикаты
**не вызывались**. Ядра `fused_rmsnorm_linear` / `fused_rope_attention`
компилировались в metallib, но `PagedAttention.cpp` и путь нормализации о них
не знают. Включать их без сверки с эталоном — риск неверных результатов.

**Решение:** флаг удалён.

### `--speculative-decoding` — функция уже всегда включена
```cpp
// Engine.cpp, было — цикл с пустым телом
for (uint32_t i = 0; i < maxDraft && ...; ++i) {
  if (!speculativeDecoding_->shouldAcceptDraft(rate)) break;
}
```
Тело пустое: считался `acceptanceRate` и сразу выход. На `draftedTokens`
влияния нет.

Главное: спекулятивное декодирование в движке **уже работает всегда** — DFlash
draft + 8 verify-строк. Живые логи показывают `2.5–4.9 tok/cycle`, то есть
больше одного токена за проход. Ширина драфта — `targetVerifyRows = 8`,
compile-time константа, вшитая в геометрию арен, запуск ядер и `static_assert`.
Флагу нечего включать.

**Решение:** флаг удалён.

### `--lazy-ane-allocation` — проводка обрывалась
Флаг доходил до `config.resources`, но `AneFfnSetting::lazyAllocation`
никому не присваивался → до `startAneFfn()` не доходил. Отдельно: ранний
возврат отдавал `outcome.context = 0`, а `Bootstrap.mm:284` берёт оттуда
`maxContext` → движок падал с `context and vocabulary sizes must be positive`.

Также `LazyAneAllocator` в `Engine` был мёртвым дублёром: реальная логика
живёт в `AneFfnStartup.cpp:106` через `setting.lazyAllocation`.

**Исправлено:** проводка в `main.mm`, ранний возврат перенесён в `decide()` с
корректным `without`, мёртвый дублёр удалён. Покрыто регрессионным тестом
`testLazyAllocationDefersButKeepsTheContext()`.

## Стало: 3 флага, все работают

| Флаг | Что делает | Эффект на этой модели |
|---|---|---|
| `--vision-text-only` | не грузит vision-башню | **+28 672 токена** (180 217 → 208 889) |
| `--lazy-ane-allocation` | откладывает ANE FFN split | контекстно-нейтрален; ANE на этой модели и так не стартует |
| `--kv-defragmentation` | собирает застрявшие страницы, освобождает экстенты | контекстно-нейтрален; эффект под фрагментацией |

Удалённый мёртвый код: 16 файлов, бинарь 2 713 304 → 2 666 744 B (−46 KB).

## Живая проверка (2026-10-17, M5 Pro 24 GiB)

Каждая конфигурация — отдельный запуск сервера, контекст из `/v1/models`,
скорость из строки `Done ·` в логе (она печатается только после завершённого
запроса).

| Конфигурация | Контекст | Скорость |
|---|---|---|
| baseline | 180 217 | 72,6 tok/s |
| `--lazy-ane-allocation` | 180 217 | 36,4 tok/s |
| `--kv-defragmentation` | 180 217 | 84,8 tok/s |
| `--vision-text-only` | **208 889** | 53,9 tok/s |
| все три | **208 889** | 51,1 tok/s |
| все три + `--persistent-cache` | **208 889** | 50,7 tok/s |

Разброс скорости между запусками (36–85 tok/s) — тепловой и от состояния
памяти, а не эффект флагов: контекст воспроизводится точно, скорость на одной
и той же конфигурации гуляет. Утверждать ускорение от флагов по этим числам
нельзя; подтверждён только прирост контекста от `--vision-text-only`.

Удалённые флаги теперь отвергаются парсером:
`error: unrecognized arguments: --write-coalescing` (и так же для остальных
трёх), `--kv-format int4` → `--kv-format int4 is not implemented yet`.

## Принцип

Флаг, который молча ничего не делает, хуже отсутствующего флага: он врёт
пользователю в `--help` и прячет настоящую работу. Три флага, которые делают
что обещают, лучше семи с выдуманными процентами.
