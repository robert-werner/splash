# Splash на M5 Pro 24 ГиБ / 1 ТБ SSD: что улучшено и что ещё можно

Всё ниже — измерения на `prism-ml/Ternary-Bonsai-2-27B-gguf:PQ2_0`, не оценки.

## Рекомендуемая конфигурация

```bash
./splash serve --model prism-ml/Ternary-Bonsai-2-27B-gguf:PQ2_0 \
  --working-set 19000M \
  --vision-text-only \
  --state-format bf16 \
  --max-cache-disk 300G --persistent-cache \
  --max-batch-size 4
```

Проверено: контекст **262 144** токена (полный максимум модели), бюджет
18,55 ГиБ, macOS остаётся 5,45 ГиБ, batch 4 сохранён, SSD-кеш 78 ГиБ
персистентный.

### Лестница конфигураций (все числа измерены)

| Конфигурация | Контекст | Бюджет | macOS |
|---|---|---|---|
| по умолчанию | 180 217 | 16,76 | 7,24 |
| `--vision-text-only` | 208 889 | 16,76 | 7,24 |
| `+ --state-format bf16 --max-batch-size 1` | 217 081 | 16,76 | 7,24 |
| `--working-set 18500M` + vision off + bf16 | 258 041 | 18,07 | 5,93 |
| **`--working-set 19000M` + vision off + bf16** | **262 144** | 18,55 | 5,45 |
| `--working-set 19G` + vision off (fp32-состояния) | 262 144 | 19,00 | 5,00 |

**217 081 достигается штатными флагами**, без правок кода — это полезно знать,
если бюджет поднимать не хочется. Шаг контекста квантуется экстентом KV
(128 страниц = 136 МиБ = 4 096 токенов), поэтому промежуточные значения
«прилипают» к кратным.

## 1. Контекст: 180 217 → 262 144 ✅ сделано

Нехватка была не в модели. `maximumContextTokens()` =
`min(токены модели, kvCapacityTokens − speculativeScratchTokens)`, а ёмкость KV
бралась из бюджета, упёртого в `recommendedMaxWorkingSetSize` минус запас —
16,76 ГиБ из 24, то есть **7,24 ГиБ были недостижимы**.

Куда уходят 24 ГиБ:

| Статья | ГиБ |
|---|---|
| веса target (27B PQ2_0) | 6,75 |
| веса draft (DFlash) | 1,18 |
| веса vision | 0,87 |
| скратч prefill + decode | 1,04 |
| резервы и staging | 0,90 |
| **фиксировано** | **10,74** |
| бюджет (потолок) | 16,76 |
| динамический остаток | 6,02 |
| **из него KV** | **5,59** → 180 224 токена |

Цена токена KV — **33 280 байт** (16 слоёв × 4 KV-головы × 256 dim × 2 × int8 +
масштабы). На 262 144 токена нужно 8,13 ГиБ KV, то есть бюджет 18,43 ГиБ с
выключенным vision — всего на 1,67 ГиБ выше старого потолка, и macOS остаётся
5,57 ГиБ.

`--max-memory` этого не мог: по контракту он только понижает
(`engine_memory_plan_test` прямо это фиксирует), и `--max-memory 21G`
**принимался и молча игнорировался**. Контракт оставлен как есть; добавлен
отдельный opt-in `--working-set`, который заменяет рекомендацию Metal в роли
бюджета, с потолком «память Mac минус подушка хоста» и честным отказом:

```
--working-set 30G → leaves this Mac too little memory; pass at most 23622320128
```

Это обосновано тем, что при unified memory `recommendedMaxWorkingSetSize` —
ориентир производительности для машины, делящей GPU с десктопом, а не предел
выделения.

Результат: `hard_budget` 19,00 ГиБ, `kv_capacity` 8,76 ГиБ = 282 624 токена,
то есть контекст теперь ограничен **моделью**, а не памятью.

## 2. Скорость: GPU загружен на 99,4 %, свободного хода нет

Это главное, что меняет картину. Телеметрия `model_timing` за реальную
генерацию:

```
prefill: gpu 6125 мс / wall 6141 мс  → загрузка GPU 99,7 %
decode:  gpu 8781 мс / wall 8833 мс  → загрузка GPU 99,4 %
один цикл decode: gpu 75,5 мс / wall 75,9 мс
```

На цикл приходится **0,4 мс** не-GPU времени. То есть ускорять «убиранием
простоев», перекрытием команд, другим планировщиком или снижением накладных
расходов хоста **нечего** — их нет.

Замер времени цикла против числа рядов:

| Полос | Рядов | Цикл | Суммарно tok/s |
|---|---|---|---|
| 1 | 8 | 76,5 мс | 32,7 |
| 2 | 16 | 74,8 мс | 64,2 |
| 4 | 32 | 76,6 мс | **143,5** |

Вчетверо больше рядов — то же время цикла.

Два факта вместе («GPU занят на 99,4 %» и «ряды бесплатны») дают точный
диагноз: GPU полностью занят **конвейером весов** — чтением и деквантованием, —
а арифметика внимания для дополнительных рядов укладывается в его тень. За цикл
читается 7,93 ГиБ весов (target 6,75 + draft 1,18) за ~76 мс ≈ **111 ГБ/с**,
что при 2 битах на вес означает деквантование порядка **34 млрд весов за цикл**,
то есть ~450 млрд весов в секунду. Это и есть стена.

Практические следствия:
- **`--max-batch-size 4` почти бесплатно даёт 4,4× суммарной пропускной** —
  единственный реальный рычаг пропускной способности, и только при нескольких
  одновременных запросах.
- **Спекуляция уже даёт ×2,5** (2,5 tok/cycle против 1,0). Приёмистость
  18–27 % — не потери: ряды бесплатны, сужать драфт нельзя (−40 %, измерено).
- **Рост контекста не замедлил генерацию**: лишняя память уходит в KV-страницы,
  а не в трафик весов.
- Однопоточную скорость на этом кванте поднять нечем, кроме разгрузки FFN на
  ANE — а он заблокирован (см. ниже).


## 3. Apple Neural Engine: полностью простаивает, и это не лечится для PQ2_0

```
ane_ffn: state=off  reason="ANE FFN split needs unrotated quantized projections"
ane_ffn_bytes: 0
```

`AneFfn::unsupported()` требует `Projection::takesPlaneViews()`, то есть
`!planeInputs_ && segments.size() == 1 && !isFloat() && !rotation`. У PQ2_0 есть
**input rotation** Prism ML (`GGUF_ROTATION_BLOCK 1024`,
`kernels/shared/gguf_rotation.metal`) — преобразование Адамара по блокам входов,
без которого 2-битное квантование теряет точность.

То есть это **взаимоисключающие требования**: ANE-путь нужен неповёрнутые веса,
а 2-битная точность держится на повороте. Для этой модели ANE недоступен.

Что реально можно: взять **неповёрнутую квантизацию** той же модели (Q4_K / Q8_0
GGUF). Тогда `ane_ffn_bytes > 0` и FFN делится между ANE и GPU. Но это разме́н:
веса станут больше → KV меньше → контекст меньше. Для 262 144 токенов нужен
PQ2_0.

## 4. Metal GPU: свободных рычагов не найдено

- 16 ядер, GPU family 10, `matmul2d` (аппаратный матмул Metal 4) уже
  используется для QK и PV в paged attention.
- **Фьюжн ядер уже активен**: `norm_rms_table16_decode` считает RMSNorm и
  сразу пишет тайлы `Table16` + частичные суммы для регистрового GGUF-тайла;
  `attention_qkv.metal` применяет RoPE инлайн вместе с разбором QKV и q/k-нормами.
  Отдельных проходов нормы и поворота нет.
- Префилл FFN идёт на GPU целиком именно потому, что ANE отказал (см. выше).

## 5. SSD: квота поднята с 32 до 78 ГиБ

Автоматическая квота была 32 ГиБ. С `--max-cache-disk 300G --persistent-cache`
движок взял **78,1 ГиБ персистентного кеша** — он ограничен политикой «четверть
свободного места на томе» (322 ГиБ свободно → 78 ГиБ). Запрошенные 300 ГиБ не
берутся намеренно.

Что это даёт: KV префиксов и состояния переживают перезапуск, много диалогов
остаются «тёплыми» → резкое падение TTFT на повторяющихся промптах. На длину
контекста это **не влияет** — контекст ограничен резидентной ёмкостью KV, и
SSD-тир его не расширяет (страница должна быть в памяти, чтобы внимание её
прочло).

Чтобы кеш был больше — освободить место на диске: квота растёт как четверть
свободного.

## Что ещё осталось нереализованным

| Рычаг | Выигрыш | Цена |
|---|---|---|
| Флаг отключения draft-модели | +1,18 ГиБ → +38 048 токенов | −×2,5 скорости, и нужен второй путь декода |
| ANE через неповёрнутый квант | ~38 % FFN | больше весов → меньше контекст |

Оба уже не нужны для 262 144: контекст упёрся в максимум модели.

## int4 KV — реализован

`--kv-format int4` хранит KV в 4 битах на элемент, сохраняя тот же масштаб
fp32 на каждую пару (KV-голова, токен), что и int8.

| | int8 | int4 |
|---|---|---|
| байт на токен | 33 280 | **16 896** |
| KV-страница | 1040 KiB | **528 KiB** |
| контекст (vision off, авто-бюджет) | 208 889 | **262 144** |
| контекст **с vision** | 180 217 | **262 144** |
| нужен ли `--working-set` | да, 19000M | **нет** |

Замеры на `prism-ml/Ternary-Bonsai-2-27B-gguf:PQ2_0`, M5 Pro 24 ГиБ: одни и те
же ответы на арифметику (`17*23` → 391), факт (Canberra) и силлогизм; скорость
на коротких запросах в пределах теплового разброса (68,4/72,3 против
70,0/72,1 tok/s).

Главное следствие: **с int4 vision больше не надо отключать.** Полный контекст
модели достигается на автоматическом бюджете при включённом vision, тогда как
int8 требовал и `--vision-text-only`, и подъёма рабочего набора до 19000M.

На длинном запросе (83 287 токенов, иголка в начале — все три конфигурации
нашли её верно):

| | контекст | TTFT | декод |
|---|---|---|---|
| int4, vision включён | 262 144 | 295,6 с | 39,5 tok/s |
| int4, vision off | 262 144 | 291,0 с | 43,8 tok/s |
| int8, vision off | 208 889 | 302,5 с | 46,8 tok/s |

Префилл у int4 немного быстрее (меньше байт KV на запись), декод примерно на
6 % медленнее. То есть int4 обменивает ~6 % скорости декода на +25 % контекста
и на сохранённый vision.

Раньше здесь стояло «нет 4-битного типа в `matmul2d`». Это было неверно:
`static_assert` в `MPPTensorOpsMatMul2dImpl.h` перечисляет среди допустимых
`int4b_format` и `uint4b_format`, и тензор над упакованным байтовым
указателем скармливается аппаратному матмулу без деквантизации
(`dev/tools/probe_int4_matmul.metal`).

Устройство: значения у int4 лежат token-major, как ключи, — тогда два
элемента одного байта это соседние dimension, то есть соседние лейны одной
группы, и байт целиком пишет чётный лейн, забирая нибб соседа через
`simd_shuffle_down`. Один писатель на байт, без атомиков. Платой за это идёт
одна асимметрия: PV-произведение у int4 не транспонирует правый операнд, а у
остальных форматов транспонирует.
